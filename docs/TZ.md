# Техническое задание v2 — CRM с таск-трекером и мессенджером

> Это исправленная версия исходного ТЗ. Список изменений и причины — в [`REVIEW.md`](REVIEW.md).
> Целевой масштаб: **команда до 5 человек** (с запасом до ~20 без изменений архитектуры).

---

## 0. Главные принципы

1. **Установить за 5 минут без знаний ИТ.** Один установщик, мастер первого запуска, никаких конфигов руками.
2. **Подключиться сотруднику за 1 минуту.** Код подключения или QR — и всё.
3. **Администрировать без консоли.** Всё — из админ-панели: сотрудники, бэкапы, место хранения, обновления.
4. **Красиво и спокойно.** Современный интерфейс, светлая и тёмная тема, цвет несёт смысл, но не кричит.
5. **Данные не теряются.** Почасовые бэкапы на отдельный носитель с проверкой восстанавливаемости.

---

## 1. Архитектура

```
┌──────────────────────── Машина хоста ────────────────────────┐
│  crm-server (системная служба, автозапуск)                   │
│   ├─ axum: REST API + WebSocket + раздача веб-интерфейса     │
│   ├─ SQLite (WAL) + FTS5 (trigram)                           │
│   ├─ воркеры: напоминания, автоархив, бэкапы                 │
│   └─ TLS (rustls, собственный локальный CA)                  │
│  crm-desktop (Tauri) — клиент + админ-панель владельца       │
└──────────────────────────────────────────────────────────────┘
          ▲ HTTPS/WSS                 ▲ HTTPS/WSS
   crm-desktop (сотрудник)      Браузер (любой ПК, планшет, телефон)
```

- **Сервер не зависит от окна приложения.** `crm-server` — отдельный бинарник, установленный как служба ОС (Windows Service / systemd / launchd). Закрытие окна, выход пользователя из ОС не останавливают CRM.
- **Один фронтенд.** React SPA собирается один раз; `crm-server` раздаёт его браузерам, `crm-desktop` встраивает тот же бандл.
- `crm-desktop` добавляет к вебу: системные уведомления, иконку в трее со счётчиком, автозапуск, автообновление, защищённое хранение токена.

### Стек (решения приняты)

| Слой | Технология |
|------|-----------|
| Сервер | Rust, tokio, axum, sqlx (SQLite), rustls, argon2, tokio-cron-scheduler, zstd, tracing |
| Клиент-оболочка | Tauri v2 |
| UI | React + TypeScript + Vite, Tailwind CSS, shadcn/ui (Radix), TanStack Query, lucide-react, cmdk (палитра Ctrl+K) |
| ID | UUIDv7 (текст) |
| Время | INTEGER, Unix-миллисекунды UTC |

### Cargo workspace

```
crm/
├─ Cargo.toml              # workspace
├─ crates/
│  ├─ crm-core/            # доменные типы, DTO, бизнес-правила (чистые функции, без I/O)
│  ├─ crm-server/          # axum, БД, WS, воркеры, бэкапы, CLI (`crm-server reset-owner-password`, `service install`)
│  └─ crm-desktop/         # Tauri
├─ web/                    # React SPA
├─ migrations/             # sqlx-миграции
└─ docs/
```

## 2. Установка и администрирование

### 2.1 Дистрибутивы

- Windows: `.msi` (x64). macOS: `.dmg` (Apple Silicon + Intel). Linux: `.deb`, `.AppImage`.
- Отдельно — headless-сборка `crm-server` для Linux (x64/ARM64) и Docker-образ для VPS/NAS.
- Один установщик; режим выбирается в мастере.

### 2.2 Мастер первого запуска — Хост (≤ 6 шагов)

1. **Режим:** «Я владелец — запустить новый сервер» / «Перенести сервер с другого компьютера (восстановить из бэкапа)» — см. §2.8 / «Подключиться к существующему».
2. **Место хранения** (см. §2.4) — по умолчанию предложены разумные пути, кнопки «Изменить».
3. **Аккаунт владельца:** имя, логин, пароль (индикатор надёжности) и **пароль восстановления** — им шифруются ключи сервера в бэкапах (§2.8). Мастер предлагает распечатать/сохранить его.
4. **Сеть:** порт (по умолчанию 8443, проверка занятости), автоматическое правило брандмауэра, предложение отключить спящий режим.
5. **Удалённый доступ:** «Только офис (локальная сеть)» / «Через Tailscale (рекомендуется)» / «Сервер с белым IP» — с короткой подсказкой к каждому.
6. **Готово:** экран с кодом подключения и QR, кнопка «Добавить сотрудника».

Служба регистрируется и запускается автоматически.

### 2.3 Подключение сотрудника

1. Владелец в админке: «Добавить сотрудника» → имя, логин, роль → получает **персональный код подключения** (строка вида `crm://…` + QR).
   Внутри кода: адреса хоста (локальный, Tailscale/внешний), порт, отпечаток сертификата, одноразовый инвайт (срок 72 ч).
2. Сотрудник:
   - **Десктоп:** вставляет код (или приложение само находит хост в сети через mDNS) → задаёт свой пароль → готово. Сертификат проверяется по отпечатку из кода, предупреждений нет.
   - **Браузер:** открывает ссылку из кода → один раз скачивает и устанавливает сертификат CA хоста (инструкция с картинками для Windows/macOS/Android/iOS) → задаёт пароль.
3. Устройство запоминается; повторный вход не требуется до выхода или отзыва сессии.

### 2.4 Выбор места хранения данных

Владелец выбирает **три независимых пути**:

| Что | По умолчанию | Ограничения |
|-----|-------------|-------------|
| База данных | `%ProgramData%\CRM\data` / `/var/lib/crm` / `~/Library/Application Support/CRM` | **Только локальный диск.** Сетевые диски, NAS-папки, облачные синхронизируемые папки (OneDrive, Яндекс.Диск, Dropbox, iCloud) — запрещены, мастер это проверяет. Причина: SQLite WAL повреждается на сетевых ФС. |
| Вложения | рядом с БД, `attachments/` | Локальный диск или другой локальный диск. |
| Бэкапы | — (обязательный выбор) | Любой: второй диск, USB, NAS, сетевая папка. Если это тот же физический диск, что и БД, — предупреждение «Это не защитит от поломки диска». |
| Второе место для бэкапов | выключено | Опционально; бэкап копируется туда же. |

Проверки при выборе: права на запись, свободное место (≥ 5 ГБ + прогноз), тип ФС.
Пути хранятся в `config.toml` в стандартной папке конфигурации ОС; файл правит только админка.

**Смена места хранения** — мастер «Перенести данные»: перевод сервера в режим «только чтение» → копирование → проверка целостности (`integrity_check`, сверка SHA-256 вложений) → переключение → старая папка остаётся, пока владелец не удалит её кнопкой.

### 2.5 Админ-панель (дашборд владельца)

- Статус сервера: адреса (локальный, внешний, Tailscale), порт, аптайм, версия.
- **Сотрудники:** создать, изменить роль, сбросить пароль, деактивировать, выдать новый код подключения.
- **Активные сессии:** пользователь, устройство, IP, время входа, последняя активность, кнопка «Завершить» (мгновенно).
- **Хранилище и диски:** см. §2.7 — заполненность каждого диска, что сколько занимает, прогноз, «Перенести данные».
- **Бэкапы:** последний успешный (время, размер, проверка ✓), список, «Сделать сейчас», «Восстановить», «Скачать».
- **Обновления:** текущая версия, «Обновить» (перед обновлением — бэкап).
- **Настройки:** порог «скоро дедлайн» (24 ч), срок автоархива (7 дн), лимит размера вложения (100 МБ), пороги заполнения диска (80 % / 90 %), часовой пояс организации, рабочие дни и часы, праздники (§4.5).
- **Журнал безопасности:** входы, неудачные попытки, блокировки.
- **Диагностика:** «Скачать отчёт» (логи без персональных данных) для поддержки.

### 2.6 Обновления

- Tauri updater для клиентов, служба обновляется через ту же кнопку в админке.
- Клиент при подключении сверяет версию API; при несовместимости — понятное сообщение «Обновите приложение» с кнопкой.
- Перед применением миграций БД — автоматический бэкап.

### 2.7 Мониторинг диска

Администратор всегда видит, насколько загружены диски и сколько места осталось.

**Виджет на главном экране дашборда** — по одной карточке на каждый **физический том**, где лежат данные CRM (БД, вложения, бэкапы, второе место бэкапов). Если несколько путей на одном томе — одна карточка, внутри перечислены пути.

Карточка тома:
- название и путь тома (`C:\`, `/dev/sda1`, `NAS \\server\backup`), тип (SSD/HDD/USB/сеть, если удаётся определить);
- кольцевая/полосовая диаграмма: **занято CRM / занято другим / свободно**;
- цифры: всего, свободно (ГБ и %), сколько занимает CRM;
- **прогноз:** «Хватит примерно на 14 мес.» — по среднему приросту за последние 30 дней;
- цвет состояния: зелёный (< 80 %), жёлтый (80–90 %), красный (> 90 % или прогноз < 30 дней).

**Детализация «Что занимает место»** (страница «Хранилище»):
- разбивка: база данных, индекс поиска, вложения, почасовые бэкапы, суточные бэкапы, логи, корзина;
- график роста за 30 / 90 / 365 дней (по дням);
- топ-20 самых больших вложений (файл, клиент → задача, размер, дата) с переходом к задаче;
- разбивка вложений по клиентам (топ-10);
- кнопки очистки: «Очистить корзину», «Удалить логи старше 30 дней», «Сократить хранение бэкапов» (с показом, сколько освободится, и подтверждением).

**Предупреждения:**

| Порог (настраивается) | Действие |
|---|---|
| Заполнено ≥ 80 % или прогноз < 60 дней | Жёлтый индикатор, уведомление владельцу раз в сутки |
| ≥ 90 % или прогноз < 30 дней | Красный индикатор, уведомление владельцу при каждом входе, баннер в админ-панели |
| Свободно < 2 ГБ на томе вложений | Загрузка новых вложений блокируется с понятным сообщением сотруднику; чаты и задачи работают |
| Свободно < 1 ГБ на томе БД | Режим «только чтение» + срочное уведомление; запись возобновляется автоматически, когда место появится |
| Нет места для бэкапа | Бэкап не выполняется, тревога владельцу; старые бэкапы **не удаляются** сверх обычной ротации |
| Том недоступен (отключён USB/NAS) | Красная карточка «Диск не подключён», тревога владельцу |

Технически:
- Сервер раз в 10 минут опрашивает свободное место на томах (крейт `sysinfo` / `fs2`), раз в сутки пересчитывает размеры по категориям и пишет снимок в `disk_usage_snapshots`.
- Прогноз и выбор состояния — чистые функции в `crm-core` (вход: снимки + пороги, выход: состояние + дней до заполнения), покрыты тестами.
- Данные доступны по `GET /api/admin/storage` (только роль `host`); обновление виджета по WS.


### 2.8 Переезд хоста на другой компьютер

Два сценария, один механизм — **восстановление из бэкапа**.

**А. Плановый переезд** (старый компьютер работает):
1. Старый хост: Админка → «Перенести на другой компьютер» → сервер делает свежий бэкап и создаёт **пакет переноса** `crm_move_YYYY_MM_DD.crmpack` (БД + вложения + настройки + зашифрованные ключи) в выбранную папку/на USB.
2. Старый хост переходит в режим **«Переехал»**: запись запрещена, клиенты получают сообщение «Сервер переезжает». Это исключает расхождение данных на двух машинах.
3. Новый компьютер: установщик → «Перенести сервер» → выбрать пакет → ввести пароль восстановления → выбрать места хранения → восстановление → проверка целостности → запуск.

**Б. Аварийный переезд** (старый компьютер сломался):
1. Новый компьютер: «Перенести сервер» → указать **папку бэкапов** (USB/NAS) → мастер сам находит последний целый бэкап БД, вложения и ключи → пароль восстановления → восстановление.
2. Мастер показывает, на какой момент восстановлены данные («Данные на 13.11.2026 14:00 — потеряно не более 1 часа работы»).

**Что переносится:** БД, вложения, настройки, учётные записи и сессии сотрудников, **CA-сертификат и ключ** сервера. Для этого при каждом бэкапе рядом с ним лежит `keys.enc` (ключи, зашифрованные паролем восстановления: Argon2id + XChaCha20-Poly1305) и `config.json` (настройки без путей).

**Переподключение сотрудников — без участия администратора:**
- CA сохранён → сертификаты остаются доверенными, сессии действуют, повторный вход не нужен.
- Клиент помнит все известные адреса хоста; если ни один не отвечает — ищет хост в локальной сети по mDNS (по идентификатору сервера, а не по IP). При использовании Tailscale новый компьютер получает то же имя хоста.
- Если хост не найден — экран «Сервер не найден» с полем «Новый адрес или код подключения»; владелец может разослать новый общий код переезда (без нового пароля).

**Если пароль восстановления утерян:** данные восстанавливаются полностью, но создаётся новый CA — сотрудникам придётся один раз заново подключиться по новому коду (пароли сохраняются).

## 3. Безопасность и роли

### 3.1 Транспорт

- Только HTTPS/WSS (rustls). При первом запуске хост генерирует **собственный CA** и сертификат сервера, подписанный им (SAN: все локальные IP, имя хоста, `.local`, Tailscale-имя).
- Десктоп-клиент доверяет серверу по отпечатку из кода подключения (TOFU + pinning).
- Браузеры — через установленный CA хоста. При использовании Tailscale возможен штатный сертификат `*.ts.net`.

### 3.2 Аутентификация (v1 — без 2FA)

- Логин + пароль, хеш **argon2id**.
- Регистрация устройства только по **персональному одноразовому инвайту**.
- Сессия: непрозрачный случайный токен (256 бит), в БД хранится его SHA-256. Привязан к `device_id` (генерируется клиентом при первом входе: Tauri — хранилище ОС, браузер — IndexedDB).
- Срок жизни сессии — 30 дней скользящий; отзыв — мгновенный (WS закрывается).
- Защита от перебора: 5 неудачных попыток → блокировка пары логин+IP на 15 мин; запись в журнал.
- Сброс пароля сотрудника — владелец в админке. Сброс пароля владельца — `crm-server reset-owner-password` на машине хоста.
- **2FA (TOTP) — в плане v2.**

### 3.3 Роли (RBAC)

В v1 — только роли, без гранулярных прав.

| Действие | Host | Manager | Employee |
|----------|:---:|:---:|:---:|
| Админ-панель, бэкапы, хранилище | ✓ | — | — |
| Управление сотрудниками | ✓ | — | — |
| Все клиенты и задачи, все чаты | ✓ | — | — |
| Клиенты и задачи своих групп | ✓ | ✓ | — |
| Создавать клиентов, задачи, назначать, менять дедлайны | ✓ | ✓ (в своих группах) | — |
| Видеть назначенные ему задачи и их чаты | ✓ | ✓ | ✓ |
| Менять статус, отмечать этапы, писать в чат своих задач | ✓ | ✓ | ✓ |
| Удаление (в корзину) | ✓ | ✓ (своё) | — |
| Окончательное удаление, очистка корзины | ✓ | — | — |

- **Группа** — набор сотрудников; клиент принадлежит одной группе. Manager видит клиентов групп, где он состоит.
- Employee, назначенный на подзадачу, видит саму подзадачу и **только названия** родительских задач (путь), без их содержимого и чатов.
- Все проверки прав — в одном месте (`crm-core::access`), включая фильтрацию результатов поиска.

## 4. Функциональные модули

### 4.1 Клиенты

**Клиент — это учётная запись для группировки задач**, а не пользователь системы:
- клиенты **не имеют логина и доступа к серверу**, ничего не видят и не получают уведомлений;
- продаж, сделок, воронки, счетов в системе **нет** — только задачи по клиенту.

Карточка (минимальная): название/ФИО, тип (физлицо/компания), **описание** (Markdown: кто это, суть работы с клиентом, при необходимости реквизиты и адрес), контакты (телефон, email), группа, ответственный менеджер, теги.
Главное на карточке — **дерево задач клиента** и сводка: открыто / просрочено / завершено за 30 дней.

### 4.1.1 Импорт и экспорт клиентов

**Импорт** (Manager, Host) — мастер из 4 шагов:
1. Загрузить файл: `.xlsx`, `.csv` (UTF-8 или Windows-1251, разделитель `;`/`,` — определяются автоматически). Есть кнопка «Скачать шаблон».
2. Сопоставить колонки с полями — автоматически по названиям заголовков («ФИО», «Название», «Телефон», «Email», «Описание», «Теги», «Менеджер»), можно поправить вручную.
3. Предпросмотр: таблица с подсветкой ошибок по строкам (пустое название, неизвестный менеджер) и **поиском дублей** (совпадение нормализованного названия, телефона или email). Для дублей выбор: пропустить / обновить / создать новый.
4. Импорт одной транзакцией (всё или ничего) → отчёт «Создано 120, обновлено 5, пропущено 3». Каждый импорт — отдельная партия, её можно **отменить в течение 24 ч** (удаляются клиенты этой партии, у которых ещё нет задач).

**Экспорт** (в пределах прав пользователя):
- Клиенты → `.xlsx` / `.csv` (с текущими фильтрами).
- Задачи (по клиенту или по фильтру) → `.xlsx`: клиент, путь задачи, статус, приоритет, исполнители, дедлайн, дата завершения, прогресс этапов.
- Владелец: «Полная выгрузка» → ZIP (все таблицы в `.xlsx` + вложения) — для архива или перехода на другую систему.

### 4.2 Задачи

- Дерево: у клиента неограниченно корневых задач и подзадач (`parent_task_id`).
- Поля: название, описание (Markdown), приоритет 1/2/3, статус, исполнители, `created_at`, `deadline_at`, `completed_at`, `archived_at`.
- **Подзадача** — полноценная задача (исполнители, дедлайн, чат). **Этап** — пункт чек-листа внутри задачи (галочка + порядок), прогресс-бар = доля отмеченных этапов.
- Правила:
  - дедлайн подзадачи ≤ дедлайна родителя;
  - задачу нельзя завершить, пока открыты её подзадачи (этапы не блокируют — только предупреждение);
  - переоткрытие завершённой задачи сбрасывает `completed_at`.
- Виды: дерево (в карточке клиента), список с фильтрами, канбан (New / In progress / Completed), «Мои задачи».

### 4.3 Визуальная индикация

Статус и дедлайн — **разные индикаторы**. Индикатор дедлайна вычисляется, не хранится:

```
fn deadline_state(task, now, warn_hours) -> DeadlineState
  Completed          → Done
  now > deadline     → Overdue
  deadline-now < warn → DueSoon
  иначе              → Ok
```

| Состояние | Отображение |
|-----------|-------------|
| `new` | нейтральная серо-синяя метка «Новая» |
| `in_progress` + Ok | зелёная полоса слева, «Осталось 3 дня» |
| DueSoon | янтарная/красная полоса, «Осталось 5 ч» |
| Overdue | красная полоса, красный текст «Просрочено на 2 ч», иконка ⚠ |
| `completed` | название зачёркнуто, карточка приглушена (opacity 60 %) |

- Приоритет — отдельная метка с иконкой: P1 (флажок, тёмно-красный), P2 (оранжевый), P3 (серый). Не смешивается с цветом дедлайна.
- Цвет **никогда не единственный** признак — всегда есть текст или иконка.

### 4.4 Автоархив

Воркер раз в час: задачи `completed`, у которых `completed_at` старше N дней (по умолчанию 7) и все подзадачи тоже завершены, получают `archived_at` (всё поддерево). Архив — отдельный раздел, задачу можно вернуть.

### 4.5 Напоминания и уведомления

- Расписание: P1 — за 24 ч, 4 ч, 1 ч; P2 и P3 — за 24 ч. Плюс «просрочено».
- Идемпотентность: запись в `reminders_sent (task_id, user_id, kind, deadline_at)` с UNIQUE — после перезапуска повторов нет; перенос дедлайна → новый цикл.
- Пропущенные за время простоя сервера — одно сводное уведомление.
- **Тихие часы (рабочее время):**
  - Владелец задаёт рабочие дни (по умолчанию Пн–Пт), рабочие часы (09:00–19:00), часовой пояс организации и список праздничных/нерабочих дат (можно загрузить производственный календарь).
  - Напоминание, время которого попадает в нерабочее время, **переносится на начало следующего рабочего периода**. Если несколько напоминаний по одной задаче перенеслись на один момент — отправляется одно, самое срочное.
  - Если дедлайн сам наступает раньше начала следующего рабочего периода, напоминание отправляется **за час до конца последнего рабочего дня перед ним** (например, дедлайн в субботу 10:00 → напоминание в пятницу в 18:00). Уведомление «просрочено» в нерабочее время всегда ждёт утра.
  - Сообщения чата в тихие часы видны в приложении, но без звука и системных уведомлений ОС.
  - Сотрудник может включить «Получать уведомления всегда» для себя.
  - При установке дедлайна на нерабочее время интерфейс предупреждает: «Это суббота — оставить?»
- Каждое уведомление сохраняется в `notifications`; онлайн-клиенты получают его по WS сразу, офлайн — при подключении.
- Каналы: колокольчик со счётчиком в UI, звук (отключаемый), системное уведомление ОС (Tauri / Web Notifications), счётчик на иконке в трее.

### 4.6 Чат задачи и «Мессенджер»

- У каждой задачи — свой чат: текст (Markdown-lite), ответ на сообщение, вложения, редактирование своих сообщений (15 мин), системные записи.
- **Системные записи (audit trail)** создаются автоматически при: смене статуса, дедлайна, приоритета, исполнителей, отметке этапа, добавлении подзадачи. Пример: «Алексей отметил этап «Согласовать договор» · 14:30».
- **Мессенджер:** слева треды «Клиент → Задача» с бейджем непрочитанных, приоритетом и полосой дедлайна; сортировка по последнему сообщению; фильтры: клиент, приоритет, статус, «только непрочитанные». Справа — чат и краткая карточка задачи.
- **Непрочитанные — у каждого пользователя свои.** Прочитанность хранится отдельно для каждой пары «пользователь — чат задачи»: `chat_reads (user_id, task_id, last_read_message_id)`. Если Иван прочитал чат, у Марии он остаётся непрочитанным.
  - Непрочитанные = сообщения других людей (и системные записи о действиях других людей), созданные после `last_read_message_id`. Свои сообщения и свои действия непрочитанными не считаются.
  - Счётчик показывается: на карточке задачи (в дереве клиента, в списке, на канбане), у треда в Мессенджере, у клиента (сумма по его задачам), на пункте «Мессенджер» в меню (общая сумма), на иконке в трее и в заголовке вкладки браузера («(3) CRM»).
  - Чат считается прочитанным, когда пользователь открыл его и долистал до последнего сообщения; в списке над непрочитанными — разделитель «Новые сообщения». Есть «Отметить как прочитанное» и «Прочитать все».
  - Счётчики обновляются в реальном времени по WebSocket — каждому пользователю приходят только его цифры; прочитал на одном устройстве — обнулилось на всех его устройствах.
  - Пользователь видит счётчики только по чатам, к которым у него есть доступ.

### 4.7 Вложения

- Хранение: `attachments/<первые 2 символа sha256>/<sha256>`; одинаковые файлы не дублируются.
- Лимит размера настраивается (по умолчанию 100 МБ). Превью для изображений и PDF.
- Файл удаляется с диска, только когда на него не осталось ссылок (и после очистки корзины).

### 4.8 Поиск (Ctrl+K)

- SQLite FTS5 с токенизатором **`trigram`**: поиск по подстроке от 3 символов, регистронезависимо, кириллица работает.
- Сущности: клиенты, задачи (переключатель «включая архив»), этапы, сообщения.
- Результаты фильтруются по правам, группируются по типу, навигация стрелками, Enter — открыть.
- Палитра также выполняет команды: «Новая задача», «Новый клиент», «Перейти в Мессенджер».

## 5. Резервное копирование

- **Каждый час** (tokio-cron-scheduler): `VACUUM INTO` во временный файл → `PRAGMA integrity_check` копии → сжатие zstd → `backup_YYYY_MM_DD_HH_MM.db.zst` в папку бэкапов (и во второе место, если задано).
- **Вложения** — инкрементально: копируются только файлы, которых ещё нет в бэкапе (по хешу).
- **Ротация:** все почасовые за 48 ч; далее одна (последняя) за сутки за 30 дней; опционально — одна за месяц за 12 месяцев.
- Ротация идемпотентна: повторный запуск после сбоя даёт тот же набор файлов.
- **Восстановление** из админки: выбор копии → сервер в режиме обслуживания → текущая БД сохраняется как `before_restore_*.db` → восстановление → проверка → запуск.
- Ошибка бэкапа или отсутствие успешного бэкапа > 2 ч → уведомление владельцу и красный индикатор на дашборде.

## 6. Схема базы данных (v1)

Схема живёт в одном месте — в миграциях: [`migrations/0001_init.sql`](../migrations/0001_init.sql). Изменения схемы — только новыми файлами миграций.

Соглашения:
- Все времена — `INTEGER`, Unix-миллисекунды UTC. ID — UUIDv7 в `TEXT`.
- `PRAGMA foreign_keys = ON; journal_mode = WAL; synchronous = NORMAL; busy_timeout = 5000`.
- Архив — `tasks.archived_at`, просрочка не хранится, статус — `new / in_progress / completed` (ограничения CHECK не дают записать противоречивые состояния).
- Удаление в корзину — `deleted_at`.
- Поиск — FTS5-таблица `search_index` (токенизатор `trigram`), заполняется триггерами на `clients`, `tasks`, `task_stages`, `messages`.
- Пути хранилища (`db_path`, `attachments_path`, `backup_paths`) — в `config.toml`, не в БД (БД может переезжать).

Таблицы: `users`, `groups`, `group_members`, `invites`, `sessions`, `clients`, `import_batches`, `holidays`, `tags`, `client_tags`, `tasks`, `task_assignees`, `task_stages`, `attachments`, `messages`, `message_attachments`, `chat_reads`, `notifications`, `reminders_sent`, `audit_log`, `disk_usage_snapshots`, `settings`, `search_index`.

## 7. Дизайн

- **Стиль:** спокойный, «воздушный» интерфейс в духе Linear / Notion: много белого пространства, скругления 8–12 px, тонкие границы вместо теней, один акцентный цвет (индиго).

- **Дизайн-токены** в одном месте (CSS-переменные): цвета, отступы (шкала 4 px), радиусы, типографика. Цвета статусов/приоритетов/дедлайнов — только через токены.
- **Раскладка:** левая панель навигации (Клиенты, Задачи, Мессенджер, Архив, Админ — только владельцу), верхняя строка с поиском (Ctrl+K) и колокольчиком, контент справа. Свернуть панель — до иконок.

- **Доступность:** контраст ≥ WCAG AA, полная работа с клавиатуры, цвет не единственный носитель смысла.
- **Язык интерфейса:** русский (строки вынесены в файл локализации).
- Перед вёрсткой — макеты ключевых экранов: карточка клиента с деревом задач, задача с чатом, Мессенджер, дашборд владельца, мастер установки.

## 8. Требования к серверу (команда 5 человек)

### 8.1 Оценка нагрузки

Допущения: 5 пользователей, ~200 сообщений и ~30 вложений по ~1 МБ в рабочий день, 250 рабочих дней в год.

| Показатель | Оценка |
|-----------|--------|
| Одновременные соединения | ≤ 10 WebSocket — нагрузка на CPU пренебрежимо мала |
| RAM `crm-server` | 50–150 МБ |
| Рост БД (текст + индексы) | ~50–100 МБ в год |
| Рост вложений | **~7–8 ГБ в год** (основной потребитель места) |
| Почасовые + суточные бэкапы БД (сжатые) | ~1–3 ГБ |
| Бэкап вложений | равен объёму вложений |

### 8.2 Варианты размещения хоста

| | Минимум | Рекомендуется |
|---|---|---|
| **Офисный ПК** (на нём же работают) | 2 ядра x64 (2015+), 4 ГБ RAM, SSD с 20 ГБ свободного места, Windows 10/11 x64, macOS 12+ или Ubuntu 22.04+ | 4 ядра, **8 ГБ RAM**, SSD 256 ГБ, **второй диск/USB-диск/NAS для бэкапов** (≥ 2× объёма данных), проводная сеть, ИБП |
| **Отдельный мини-ПК / неттоп** (только сервер, headless Linux) | 2 ядра, 2 ГБ RAM, SSD 64 ГБ | 4 ядра, 4 ГБ RAM, SSD 256 ГБ, бэкап на USB-диск/NAS, ИБП |
| **Raspberry Pi 4/5** | 4 ГБ RAM, SSD по USB (не microSD) | Pi 5, 8 ГБ, NVMe |
| **VPS** (удалённая команда, белый IP, работает 24/7) | 1 vCPU, 1 ГБ RAM, 25 ГБ SSD | 2 vCPU, 2 ГБ RAM, 50+ ГБ SSD, бэкапы — на отдельное хранилище провайдера |

Обязательно для любого варианта:
- Хост включён всё рабочее время, **спящий режим отключён**.
- Сеть: локальная — от 100 Мбит/с (Wi-Fi 5 тоже подходит). Для удалённых сотрудников — исходящая скорость хоста ≥ 10 Мбит/с (отправка вложений).
- Windows: WebView2 (в Windows 11 есть; в Windows 10 ставится установщиком автоматически).
- Порт (по умолчанию 8443/TCP) открыт в брандмауэре (мастер делает это сам).

### 8.3 Клиенты

- Десктоп: Windows 10/11, macOS 12+, Linux (Ubuntu 22.04+); 4 ГБ RAM.
- Браузер: последние версии Chrome, Edge, Firefox, Safari (включая мобильные).

## 10. Требования к коду

- Workspace из трёх крейтов (§1). Бизнес-правила (права, состояния дедлайна, правила завершения/архивации, расписание напоминаний, ротация бэкапов) — **чистые функции в `crm-core`** с юнит-тестами.
- Внешние данные (HTTP-запросы, WS-сообщения, конфиг) парсятся в доменные типы на границе; внутри — только валидные типы (`TaskId`, `Priority`, `Deadline` и т. д.).
- Ошибки — `thiserror` (библиотеки) и единый `ApiError` → HTTP-ответ. В не-тестовом коде `#![deny(clippy::unwrap_used, clippy::expect_used)]`.
- Все фоновые операции идемпотентны (архивация, напоминания, ротация бэкапов).
- Логи — `tracing`, ротация файлов, без паролей и токенов.
- Тесты: юнит (`crm-core`), интеграционные (API на временной БД), e2e (Playwright) для ключевых сценариев.
- CI: `cargo fmt --check`, `clippy -D warnings`, тесты, сборка установщиков.

## 12. Глоссарий

- **Хост** — машина, где работает `crm-server`; **Владелец** — пользователь с ролью `host`.
- **Код подключения** — строка/QR с адресом хоста, отпечатком сертификата и персональным инвайтом.
- **Задача / подзадача** — элемент дерева задач клиента со своими исполнителями, дедлайном и чатом.
- **Этап** — пункт чек-листа внутри задачи.
- **Индикатор дедлайна** — вычисляемое состояние Ok / DueSoon / Overdue / Done, не хранится в БД.
- **Группа** — набор сотрудников, к которому привязаны клиенты; определяет видимость для менеджеров.
- **Клиент** — учётная запись (человек или компания), к которой привязаны задачи; не пользователь системы, доступа не имеет.
- **Тихие часы** — нерабочее время организации; напоминания переносятся на начало рабочего периода.
- **Пакет переноса** — файл `.crmpack` со всеми данными и зашифрованными ключами для переезда хоста.
- **Пароль восстановления** — пароль, которым зашифрованы ключи сервера в бэкапах.
