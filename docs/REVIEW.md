# Замечания к исходному ТЗ (ревью)

Ниже — что в исходном ТЗ противоречит само себе, чего не хватает и что сделает установку/администрирование сложнее, чем нужно для команды из 5 человек. Всё исправленное уже внесено в [`TZ.md`](TZ.md).

Обозначения: 🔴 — сломает разработку или эксплуатацию, 🟡 — важно, 🟢 — улучшение.

---

## 1. Архитектура и установка

| # | Замечание | Решение в ТЗ v2 |
|---|-----------|-----------------|
| 1.1 🔴 | **Сервер живёт внутри окна Tauri.** Владелец закрыл окно / вышел из Windows / ПК ушёл в сон — CRM у всех сотрудников легла. | Сервер — отдельный процесс `crm-server`, ставится **системной службой** (Windows Service / systemd / launchd) с автозапуском. Tauri-приложение на хосте — только клиент + админ-панель. Мастер установки отключает спящий режим (с согласия). |
| 1.2 🟡 | Два фронтенда (Tauri и браузер) = двойная работа. | Один фронтенд (React SPA), который `crm-server` раздаёт по HTTPS. Tauri-клиент — тонкая обёртка над тем же UI + нативные уведомления, трей, автообновление. |
| 1.3 🟡 | «React или SolidJS» — решение не принято. | **React + TypeScript + Vite + Tailwind + shadcn/ui (Radix)**. Причина: готовые красивые компоненты и лучшая кодогенерация. |
| 1.4 🔴 | Не описаны установка, первый запуск, обновление и версии. | Добавлен раздел «Установка и администрирование»: один установщик, мастер первого запуска, автообновление, проверка совместимости версий клиент↔хост, автобэкап перед миграцией БД. |
| 1.5 🟡 | Подключение сотрудника = вручную вбить IP, порт и токен. | **Код подключения** (строка + QR), где уже зашиты адреса, порт, отпечаток сертификата и одноразовый инвайт. В локальной сети хост ещё и находится автоматически (mDNS). |

## 2. Безопасность и сеть

| # | Замечание | Решение |
|---|-----------|---------|
| 2.1 🔴 | **Самоподписанный сертификат + вход через браузер = красный экран «Подключение не защищено»** у каждого сотрудника. Плюс браузер без HTTPS-доверия не даст системные уведомления. | Десктоп-клиент — проверка отпечатка (pinning) из кода подключения. Для браузера — хост создаёт **свой локальный CA**, админка отдаёт файл «установить сертификат» (1 клик на ПК сотрудника). При удалённой работе через Tailscale — его штатные HTTPS-сертификаты. |
| 2.2 🟡 | Один общий Invite Token на всех: утёк — может зарегистрироваться кто угодно. | Инвайт **персональный, одноразовый, со сроком жизни** (по умолчанию 72 ч). Хост создаёт сотрудника → получает его личный код подключения. |
| 2.3 🟡 | JWT + кнопка «разорвать сессию» конфликтуют: JWT нельзя отозвать мгновенно. | Для 5 человек — **непрозрачные сессионные токены в БД** (таблица `sessions`). Отзыв мгновенный, WebSocket закрывается сразу. JWT не нужен. |
| 2.4 🟡 | «Аппаратный ID» в браузере получить нельзя. | ID устройства генерируется клиентом при первом входе и хранится локально (Tauri — в защищённом хранилище ОС, браузер — в IndexedDB). |
| 2.5 🟡 | Нет защиты от перебора паролей. | Ограничение попыток: 5 неудач → блокировка на 15 мин для пары логин+IP, запись в журнал. |
| 2.6 🟢 | 2FA (TOTP) | **Убрано из v1 по решению заказчика.** Перенесено в план v2. Без 2FA защита держится на: argon2id, персональном инвайте, привязке к устройству, rate-limit и TLS. Рекомендация — не открывать порт хоста напрямую в интернет, а использовать Tailscale/WireGuard. |
| 2.7 🟡 | Нет сценария «забыл пароль» и «владелец потерял доступ». | Хост сбрасывает пароль сотрудника из админки. Пароль владельца — командой `crm-server reset-owner-password` на самой машине хоста. |
| 2.8 🟡 | Хранение персональных данных клиентов (ФИО, контакты). | Журнал действий (кто что смотрел/менял/удалял), удаление «в корзину», шифрованный бэкап (опция). Если компания в РФ — учесть 152-ФЗ. |

## 3. Модель данных — противоречия в схеме

| # | Замечание | Решение |
|---|-----------|---------|
| 3.1 🔴 | Архив задан **дважды**: `status = 'archived'` в CHECK и флаг `is_archived` в тексте. Два источника правды разойдутся. | Статус: `new / in_progress / completed`. Архив — только поле `archived_at` (NULL = не в архиве). |
| 3.2 🔴 | «Просрочено» нельзя хранить — это производное от `deadline_at` и текущего времени. | Индикатор дедлайна вычисляется функцией в `crm-core`, в БД не хранится. |
| 3.3 🔴 | **Нет таблиц**, на которые опирается текст ТЗ: исполнители задачи, группы (для «клиенты своей группы»), ответственный менеджер, теги, вложения, прочитанность (бейджи), ответы на сообщения, сессии, журнал, настройки, отправленные напоминания, FTS-индексы. | Все добавлены в схему v2. |
| 3.4 🟡 | `role` + `permissions_json` — два источника прав. Для 5 человек гранулярные права — лишняя сложность. | v1: только роли. Гранулярные права — v2. |
| 3.5 🟡 | Даты как `DATETIME DEFAULT CURRENT_TIMESTAMP` — текст, часовые пояса не определены. | Все времена — `INTEGER`, Unix-миллисекунды UTC. Отображение — в часовом поясе пользователя. ID — UUIDv7 (сортируются по времени). |
| 3.6 🟡 | Подзадачи и этапы — два способа дробить работу, правила не описаны. | Определено: **подзадача** — полноценная задача (свои исполнители, дедлайн, чат); **этап** — пункт чек-листа внутри задачи. Дедлайн подзадачи ≤ дедлайна родителя. Родителя нельзя закрыть с открытыми подзадачами. |
| 3.7 🟡 | Не описано, что видит сотрудник, назначенный только на подзадачу. | Видит свою подзадачу + названия родительских задач (путь), без их содержимого и чатов. |
| 3.8 🟢 | `messages.content NOT NULL` — сообщение «только с файлом» невозможно. | `content` может быть пустой строкой при наличии вложения (проверка на уровне API). |

## 4. Функциональность

| # | Замечание | Решение |
|---|-----------|---------|
| 4.1 🔴 | **Напоминания не идемпотентны**: после перезапуска сервера уйдут повторно; при переносе дедлайна старые напоминания «висят». | Таблица `reminders_sent (task_id, user_id, kind, deadline_at)` с UNIQUE. Перенос дедлайна → новые напоминания. Пропущенные во время простоя — одно сводное уведомление, а не пачка. |
| 4.2 🟡 | Уведомления только через WebSocket: сотрудник был офлайн — ничего не узнал. | Таблица `notifications` с флагом прочтения; при подключении клиент получает непрочитанные. |
| 4.3 🟡 | Цвет: и приоритет 1, и просрочка тяготеют к красному — пользователь не поймёт, что именно «горит». Заливка всей карточки зелёным/красным утомляет. | Приоритет — **иконка + метка** (P1/P2/P3), дедлайн — **цветная полоса слева + текст** («Просрочено на 2 ч», «Осталось 5 ч»). Цвет никогда не единственный носитель смысла (дальтоники). |
| 4.4 🟡 | Нет цвета для статуса `new`. | `new` — нейтральный серо-синий. |
| 4.5 🟡 | FTS5 со стандартным токенизатором плохо ищет по-русски: «Иванов» не найдёт «Иванову». | Токенизатор **`trigram`** (поиск по подстроке от 3 символов, регистронезависимо, в т. ч. кириллица). Результаты поиска **фильтруются по правам** пользователя. |
| 4.6 🟡 | Вложения упомянуты, но не специфицированы. | Хранение по SHA-256 (без дублей), лимит размера (по умолчанию 100 МБ), счётчик ссылок для удаления, превью картинок/PDF, бэкап — инкрементальный. |
| 4.7 🟢 | Архив: что с архивацией родителя, у которого есть активные подзадачи? | Архивируется только завершённая задача, у которой все подзадачи тоже завершены; архивируется поддерево целиком. |

## 5. Резервное копирование

| # | Замечание | Решение |
|---|-----------|---------|
| 5.1 🟡 | «Online Backup API (VACUUM INTO)» — это **два разных механизма**. | Выбран `VACUUM INTO` (работает через sqlx, даёт сжатую консистентную копию). |
| 5.2 🔴 | Бэкап на тот же диск, что и БД, — не бэкап: умер диск — умерло всё. | Хост выбирает **отдельное место для бэкапов** (второй диск, USB, NAS). Мастер предупреждает, если это тот же физический диск. |
| 5.3 🔴 | Бэкап, который ни разу не восстанавливали, может оказаться битым. | После каждого бэкапа — `PRAGMA integrity_check` копии. Кнопка «Восстановить из бэкапа» в админке и ежедневная проверка последнего архива. |
| 5.4 🟡 | Не сказано про бэкап вложений. | Вложения копируются инкрементально (по хешу — копируются только новые файлы). |
| 5.5 🟢 | Нет статуса бэкапов для администратора. | На дашборде: время последнего успешного бэкапа, размер, свободное место; при ошибке — уведомление владельцу. |

## 6. Выбор места хранения (новое требование)

| # | Замечание | Решение |
|---|-----------|---------|
| 6.1 🔴 | **SQLite в режиме WAL нельзя держать на сетевом диске** (SMB/NFS, папка NAS, облачные папки Яндекс.Диск/OneDrive/Dropbox) — база будет повреждена. | Для БД разрешён **только локальный диск**; мастер это проверяет и запрещает сетевые/синхронизируемые папки. Для бэкапов сетевой диск разрешён. |
| 6.2 🟡 | Нужно раздельно выбирать, где лежит что. | Три пути: **БД**, **вложения**, **бэкапы**. Плюс опционально второе место для бэкапов. Смена пути — мастером «Перенести данные» с проверкой. |
| 6.3 🔴 | Не определено, что делать, когда диск заполняется: SQLite при нехватке места начнёт падать на записи, бэкапы молча перестанут создаваться. | Мониторинг каждого тома на дашборде (занято/свободно/прогноз, разбивка по категориям), пороги 80/90 %, мягкая деградация: сначала блокируются вложения, затем — режим «только чтение» (§2.7 ТЗ). |

## 7. Удалённый доступ

| # | Замечание | Решение |
|---|-----------|---------|
| 7.1 🟡 | Проброс портов на роутере — сложно для неспециалиста и опасно без 2FA. | Рекомендуемый путь — **Tailscale** (ставится за 2 минуты, без проброса портов). Альтернатива — хост на VPS. Прямой проброс порта — только для опытных, с предупреждением в админке. |

|---|-----------|---------|
| 8.1 🟡 | Нет разбивки на этапы — «сразу всё» приведёт к большой и неработающей первой версии. | Добавлен план этапов MVP → v1 → v2 с критериями приёмки. |
